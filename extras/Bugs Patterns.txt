## PATTERN 1 — Session State Set Before Auth Completes
**المشكلة:** تعيين `_active_client_ws` أو `_active_client_ip` قبل إتمام HMAC/PIN
**أمثلة حقيقية:** C4 (WS)، M18 (DC)
**القاعدة:** أي كود بيعمل `_active_client_ws = X` لازم يكون **بعد** `hmac_ok` وبعد PIN verification

```python
await send_hmac_challenge()     # auth comes after

# ✅ CORRECT
await complete_hmac_auth()      # auth first
_active_client_ws = ws          # then set
```

## PATTERN 5 — Blocking Call in Async Function
**المشكلة:** `os.stat`, `os.walk`, `time.sleep` في `async def` بيبلوكوا الـ event loop
**أمثلة حقيقية:** H12, Audit-C4, Audit-C5, Audit-C6, Audit-C7
**القاعدة:** أي I/O أو CPU-heavy operation في async function لازم يكون في `run_in_executor` أو `await asyncio.sleep()`
```python
# ❌ WRONG
async def handler():
    stat = os.stat(path)  # blocks event loop
    time.sleep(0.1)       # blocks event loop
    thread.join(timeout=1) # blocks event loop

# ✅ CORRECT
async def handler():
    loop = asyncio.get_running_loop()
    stat = await loop.run_in_executor(None, os.stat, path)
    await asyncio.sleep(0.1)
    await loop.run_in_executor(None, thread.join, 1.0)
```

## PATTERN 8 — Stale Timestamps in Queued Messages
**المشكلة:** messages بتتبني بـ `_ts:Date.now()` وقت الـ emit، لو اتبعتوا بعد وقت طويل بيترفضوا بالـ replay protection
**مثال حقيقي:** N1 — `_wsQueue` بيحتفظ بـ messages بـ `_ts` قديم
**القاعدة:** الـ `_ts` لازم يتضاف وقت الـ send مش وقت الـ queue
```javascript

// ✅ CORRECT — _ts added at send time
_wsQueue.push(JSON.stringify({_ev:event, ...data}));
// on flush: add fresh _ts
_wsQueue.forEach(m => {
    var d=JSON.parse(m); d._ts=Date.now();
    _ws.send(JSON.stringify(d));
});
```

## PATTERN 19 — Custom Server Handler Parameters Not Auto-Injected

## PATTERN 22 — WebSocket Fragmentation Not Reassembled
**المشكلة:** RFC 6455 §5.4 بيسمح بـ fragmented messages (FIN=0 على frames غير الأخيرة، opcode 0x0 للـ continuations) — لو الـ server بيرجع أول frame بس، الباقي بيضيع

**القاعدة:** أي WebSocket receive لازم يعيد تجميع fragments حتى FIN=1
```python
# ✅ CORRECT — reassemble fragments
async def _recv_message(self):
    opcode = None
    fragments = []
    while True:
        # ... read frame ...
        if opcode is None:
            opcode = frame_opcode  # first frame sets opcode
        elif frame_opcode != 0x0:
            raise WebSocketDisconnect(1002)  # protocol error
        fragments.append(payload)
        if fin:
            return opcode, b''.join(fragments)
```

## PATTERN 32 — Dead Async Computation in Nested `.then()` Chains
**المشكلة:** في nested Promise chains، الـ outer `.then()` result بيتحسب لكن النتيجة مش بتتستخدم — الـ inner chain بتوصل للـ original value عبر closure بدل ما تستخدم الـ result المحسوب
**مثال حقيقي:** P4 — `reportPinResult` في client: `_sha256(pin).then(function(hashedPin){...})` بتحسب `hashedPin` لكن الـ inner chain بتعمل `_sha256(salt+pin)` وتبعت `saltedHash` — `hashedPin` مش بتتستخدم خالص
**القاعدة:** في nested Promise chains، افحص إن كل `.then()` result بيتستخدم فعلاً. لو الـ inner code بتوصل للـ original value عبر closure بدل النتيجة المحسوبة، الـ outer computation هو dead code
```javascript
// ❌ WRONG — hashedPin computed but never used
_sha256(pin).then(function(hashedPin) {   // dead result
    _sha256(salt + pin).then(function(saltedHash) {
        send(saltedHash);  // uses closure var 'pin', not 'hashedPin'
    });
});

// ✅ CORRECT — remove dead outer computation
var saltedInput = salt ? salt + pin : pin;
_sha256(saltedInput).then(function(saltedHash) {
    send(saltedHash);
});
```

## PATTERN 33 — Non-Reentrant Lock Re-acquired (Self-Deadlock)
**المشكلة:** كود بياخد `threading.Lock` ثم ينادي method تانية بتاخد **نفس** الـ lock → تجمّد أبدي. خطير بشكل خاص لما الـ lock يكون alias لـ lock داخلي
**مثال حقيقي:** هذه الجلسة — `_ws_pin_lock` كان alias لـ `_session._lock`؛ `with _ws_pin_lock:` ثم `_session.set_verified()` (اللي بتاخد `self._lock`) → السيرفر بيتجمد عند كل WebSocket connect
**القاعدة:** أي method بتُنادى داخل `with lock:` ممنوع تاخد نفس الـ lock. استخدم `RLock` أو عدّل المتغير مباشرة بدل استدعاء method تقفل
```python
# ❌ WRONG — _ws_pin_lock IS _session._lock
with _ws_pin_lock:
    _session.set_verified(ip, True)   # tries to take self._lock again → deadlock

# ✅ CORRECT — mutate the shared dict directly under the lock
with _ws_pin_lock:
    _ws_pin_verified[ip] = True
```

## PATTERN 35 — Blocking File I/O Logger Called From Async Handlers
**المشكلة:** دالة logging بتعمل `open()+write()` متزامن وبتتنادى من `async def` handlers → بتبلوك الـ event loop مع كل log (كل connect / key press)
**مثال حقيقي:** هذه الجلسة — `_log_event` كانت تفتح وتكتب الملف synchronously داخل index()/websocket/auth handlers
**القاعدة:** الـ logging من async context لازم يكون عبر طابور + خيط كاتب واحد (single-writer)؛ الـ hash-chain فقط يتم under-lock بسرعة
```python
# ✅ CORRECT — fast in-memory chain under lock, file write offloaded
_log_write_queue = queue.Queue(maxsize=10000)
def _log_writer_thread():
    while True:
        line = _log_write_queue.get()
        with open(LOG_FILE,'a',encoding='utf-8') as f: f.write(line+'\n')
def _log_event(...):
    with _log_lock: line = _build_chained_entry(...)   # fast
    try: _log_write_queue.put_nowait(line)             # never blocks loop
    except queue.Full: pass
```

## PATTERN 37 — Client/Server Clock Skew Breaks Replay Window (Silent Drop)
**المشكلة:** حماية الـ replay بترفض أي رسالة فرق توقيتها أكبر من نافذة صغيرة (مثلاً 2s). ساعة الموبايل/الكلاينت غالباً منحرفة ثوانٍ → **كل** أحداث الإدخال تُرفض **بصمت** → "كل حاجة معطلة" رغم أن الاتصال شغّال
**مثال حقيقي:** هذه الجلسة — `if abs(time.time() - _ts/1000) > 2: return` كان يرمي كل أحداث الماوس/الكيبورد على موبايل بساعة منحرفة

```python
# server: send time at auth
await ws.send_json({'type':'hmac_ok','server_ts':int(time.time()*1000)})
# client: offset = server_ts - Date.now();  stamp _ts = Date.now()+offset
```

## PATTERN 39 — COM/Native Object Double-Free or Wrong Release (`del` vs API)

```python
def close(self):
```

## PATTERN 41 — Fixed Quality + Unbounded Rate = Jitter on Weak Hardware
**المشكلة:** السيرفر يثبّت الجودة (اختيار اليوزر) ويترك معدل الالتقاط/الإرسال يجري بأقصى سرعة. على معالج ضعيف، زمن ترميز الفريم متغيّر وقريب من الـ budget → الـ fps والـ CPU يتأرجحان بعنف (11↔30)
**مثال حقيقي:** هذه الجلسة — معالج 2016 (A12) أعطى عداد متذبذب واستهلاك CPU 30-44% غير ثابت
**القاعدة:** طبّق **adaptive frame pacing**: قِس زمن الترميز الفعلي (EMA)، احسب الـ fps المستدام (مع headroom)، وقيّد معدل الالتقاط له (السقف = اختيار اليوزر). هذا يثبّت النعومة دون لمس الجودة — نفس مبدأ TeamViewer/DeskRT
```python
# emit task measures encode time; capture loop paces to sustainable fps
if enc_ema>0: sustainable = 0.85/enc_ema
eff_fps += max(-2, min(2, min(user_fps, sustainable) - eff_fps)) * 0.5
frame_budget = 1.0 / max(1.0, min(user_fps, eff_fps))
```

## PATTERN 42 — Subprocess Capture Backend Ordered Before In-Process Ones
**المشكلة:** ترتيب fallback يضع backend بيفتح subprocess دائم (ffmpeg) أو per-frame (scrot) **قبل** backends داخل العملية (mss/xlib) → استهلاك أعلى وخطر تعليق صامت لو الـ subprocess علّق
**مثال حقيقي:** هذه الجلسة — Linux X11 chain كان `ffmpeg_x11 → xlib → mss`؛ الأصح `mss → xlib → ffmpeg_x11 → scrot`
**القاعدة:** رتّب backends الالتقاط: in-process السريع/المستقر أولاً، ثم subprocess كاحتياطي. تأكد أن كل فرع (Wayland/X11) عنده fallback نهائي (mss)
```python
# ✅ X11 order
chain.append((_MSSCaptureBackend, 'mss'))          # in-process, stable
chain.append((_XlibCaptureBackend, 'python-xlib')) # in-process
chain.append((_FFmpegX11CaptureBackend,'ffmpeg_x11')) # persistent subprocess (fallback)
chain.append((_ScrotCaptureBackend,'scrot'))       # per-frame subprocess (last)
```

## PATTERN 58 — Layered Input Backends With Graceful Fallback (Cross-Platform Parity)
**المشكلة:** الاعتماد على subprocess واحد لكل منصة (xdotool/osascript) = بطيء (process fork لكل حدث) وغير متكافئ: Windows عنده SendInput (kernel) بينما Linux/macOS عالقين على subprocess

- Linux Wayland: evdev/uinput (يعمل بدون X11) → xdotool/XWayland

```python
def moveRel(dx,dy):
    if _have_xtest:
        try: _xtest_move(dx,dy); return
        except Exception: pass
    if _have_uinput:
        try: _uinput_move(dx,dy); return
        except Exception: pass
    _xdotool(...)   # universal fallback
```

## PATTERN 65 — استخراج موديول يشارك dict/list قابل للتغيير: خطر الـ Aliasing
**المشكلة:** عند نقل دوال أمنية/حالة لموديول منفصل، الـ state المشترك (مثل `security` dict) بيتكتب من أماكن في السيرفر (watcher بيعمل `.clear()/.update()`، approve بيعمل `.append()`) **ويُقرأ** من الموديول. لو الموديول استورد **نسخة** (أو أعاد بناء dict خاص به)، الكتابة من السيرفر مش هتظهر في الموديول والعكس → ثغرة صامتة: IP يتشال من blacklist بس الموديول لسه شايفه، أو whitelist جديدة متظهرش. `py_compile` + HTTP بيعدّوا بنجاح لأن المشكلة في **هوية الـ object** مش في الـ syntax.
**القاعدة:** شارِك **نفس الـ reference** عبر injection (مش نسخة)، واكتب اختبار aliasing صريح:
```python
mod.configure(security, sec_lock)      # نفس الـ object
security['whitelist'].append('X')       # كتابة من جهة السيرفر
assert mod._is_allowed('X')            # لازم تظهر فوراً في الموديول
security['blacklist'].append('Y')
assert not mod._is_allowed('Y')        # blacklist تغلب whitelist
```
+ أضف parity test: استخرج دوال الـ backup الأصلية بـ regex، نفّذها في sandbox، وقارن نتيجتها سطر بسطر مع الموديول الجديد بنفس المدخلات (allow/blacklist، nonce reuse، rate-limit sequence، HMAC good/bad).
- [ ] هل الموديول المستخرج يشارك نفس reference للـ state القابل للتغيير (مش نسخة) + اختبار aliasing + parity مقابل الأصل؟ (Pattern 65)

## PATTERN 67 — استخراج Scalar Config (int/bool) القابل للتغيير في runtime: خطر الـ Snapshot
**المشكلة:** عند استخراج إعدادات لموديول، الإغراء إنك تنقل **كل** الإعدادات بما فيها الأعلام المتغيّرة (FLAG_SCALE, FLAG_GREY...). لكن لو الإعداد **scalar** (int/bool/str) وبيتكتب live في runtime (من handler زي `/flags/update`)، نقله لموديول بـ alias في السيرفر (`FLAG_SCALE = pd_config.FLAG_SCALE`) **يكسر التحديث الحي بصمت**: الـ alias بياخد **snapshot للقيمة وقت الإقلاع**، فلما الـ handler يحدّث `pd_config.FLAG_SCALE` الـ alias القديم في السيرفر مايتغيّرش (لأن int/bool ممرّرة بالقيمة مش بالـ reference — عكس الـ dict/list). النتيجة: الميزة "تشتغل" بدون error بس بقيمة قديمة forever. الفرق عن نمط 65: هناك dict/list ممكن مشاركتهم بـ reference؛ هنا scalar **مستحيل**.
**القاعدة:**
- انقل **الثوابت الـ immutable فقط** (تُكتب مرة وقت import وتُقرأ بس) — دي آمنة لأن مفيش mutation.
- الإعدادات الـ mutable الـ scalar: **سِيبها في مكانها** لحد ما تعمل redesign لـ object واحد (`cfg.scale` بدل `FLAG_SCALE`) — وقتها الـ mutation عبر `cfg` reference وتظهر في كل مكان.
- لو لازم تنقلها قبل الـ redesign: **حوّل كل القراءات** لـ `pd_config.FLAG_X` (مش alias) — مايصحش تسيب alias scalar في السيرفر أبداً.
```python
# غلط (snapshot — يكسر live-update بصمت):
FLAG_SCALE = pd_config.FLAG_SCALE      # أخدت القيمة دلوقتي وبس
# صح (إما immutable في موديول، أو قراءة مباشرة دايماً):
if pd_config.FLAG_SCALE != 1.0: ...     # يقرأ القيمة الحية كل مرة
```
- [ ] هل الإعداد المنقول immutable؟ لو mutable scalar: هل تجنّبت الـ alias واستخدمت `pd_config.X` مباشرة (أو أجّلته لـ redesign)؟ (Pattern 67)

**المشكلة:** 51 route بتعتمد على عشرات الـ globals (FLAG_*, security, _stream, manager, _log_event, إلخ). محاولة نقلها لموديول منفصل بـ dependency injection = حقن 30+ dependency لكل route. ده redesign مش استخراج.
**القاعدة:** لو الـ handlers بتلمس **كل حاجة**، سيبها في السيرفر الرئيسي مع الموديولات الفرعية. التقسيم هنا مش هيقلل التعقيد، هيخفيه بس.
- [ ] هل نقل الـ routes يتطلب injection ضخم؟ لو أيوه، سيبها في السيرفر ووثّق السبب. (Pattern 68)

## PATTERN 69 — Main Loop + Lifespan: الـ globals اللي بيتكتبوا في الـ workers
**المشكلة:** الـ main loop (`__main__`) والـ lifespan workers بيستخدموا `global` للكتابة (screen_streaming, audio_streaming, FLAG_*, إلخ). الـ workers بتشتغل في threads منفصلة وتحتاج نفس الـ global namespace.
**القاعدة:** الـ lifespan ده **قلب السيرفر** — نقله لموديول بيتطلب نقل الـ global namespace كله. الأفضل نسيبه في `__main__` ونوثّق الـ dependencies بوضوح.
- [ ] هل الـ workers بيكتبوا في globals السيرفر؟ لو أيوه، نقلهم لموديول هيحتاج redesign كامل. (Pattern 69)
