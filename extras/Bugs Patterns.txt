## PATTERN 5 — Blocking Call in Async Function
**Problem:** `os.stat`, `os.walk`, `time.sleep` in `async def` block the event loop
**Real Examples:** H12, Audit-C4, Audit-C5, Audit-C6, Audit-C7
**Rule:** Any I/O or CPU-heavy operation in an async function must use `run_in_executor` or `await asyncio.sleep()`
```python
# ❌ WRONG
async def handler():
    stat = os.stat(path)  # blocks event loop
    time.sleep(0.1)       # blocks event loop
    thread.join(timeout=1) # blocks event loop

# ✅ CORRECT
async def handler():
    loop = asyncio.get_running_loop()
    stat = await loop.run_in_executor(None, os.stat, path)
    await asyncio.sleep(0.1)
    await loop.run_in_executor(None, thread.join, 1.0)
```

## PATTERN 8 — Stale Timestamps in Queued Messages
**Problem:** Messages are stamped with `_ts:Date.now()` at emit time; if sent after a long delay they get rejected by replay protection
**Real Example:** N1 — `_wsQueue` keeps messages with stale `_ts`

```javascript
_wsQueue.forEach(m => {
    var d=JSON.parse(m); d._ts=Date.now();

});
```

## PATTERN 22 — WebSocket Fragmentation Not Reassembled
**Problem:** RFC 6455 §5.4 allows fragmented messages (FIN=0 on non-final frames, opcode 0x0 for continuations) — if the server returns the first frame only, the rest is lost
**Real Example:** Audit-WS8 — `_recv_frame()` returns the first data frame and ignores continuation frames
**Rule:** Any WebSocket receive must reassemble fragments until FIN=1
```python
# ✅ CORRECT — reassemble fragments
async def _recv_message(self):
    opcode = None
    fragments = []
    while True:
        # ... read frame ...
        if opcode is None:
            opcode = frame_opcode  # first frame sets opcode
        elif frame_opcode != 0x0:
            raise WebSocketDisconnect(1002)  # protocol error
        fragments.append(payload)
        if fin:
            return opcode, b''.join(fragments)
```

## PATTERN 32 — Dead Async Computation in Nested `.then()` Chains
**Problem:** In nested Promise chains, the outer `.then()` result is computed but never used — the inner chain reaches the original value via closure instead of using the computed result
**Real Example:** P4 — `reportPinResult` in client: `_sha256(pin).then(function(hashedPin){...})` computes `hashedPin` but the inner chain does `_sha256(salt+pin)` and sends `saltedHash` — `hashedPin` is never used at all
**Rule:** In nested Promise chains, verify that every `.then()` result is actually used. If inner code reaches the original value via closure instead of the computed result, the outer computation is dead code
```javascript
// ❌ WRONG — hashedPin computed but never used
_sha256(pin).then(function(hashedPin) {   // dead result
    _sha256(salt + pin).then(function(saltedHash) {
        send(saltedHash);  // uses closure var 'pin', not 'hashedPin'
    });
});

// ✅ CORRECT — remove dead outer computation
var saltedInput = salt ? salt + pin : pin;
_sha256(saltedInput).then(function(saltedHash) {
    send(saltedHash);
});
```

## PATTERN 33 — Non-Reentrant Lock Re-acquired (Self-Deadlock)
**Problem:** Code takes a `threading.Lock` then calls another method that takes the **same** lock → permanent freeze. Especially dangerous when the lock is an alias for an internal lock
**Real Example:** This session — `_ws_pin_lock` was an alias for `_session._lock`; `with _ws_pin_lock:` then `_session.set_verified()` (which takes `self._lock`) → server freezes on every WebSocket connect
**Rule:** Any method called inside `with lock:` must not take the same lock. Use `RLock` or mutate the variable directly instead of calling a method that locks
```python
# ❌ WRONG — _ws_pin_lock IS _session._lock
with _ws_pin_lock:
    _session.set_verified(ip, True)   # tries to take self._lock again → deadlock

# ✅ CORRECT — mutate the shared dict directly under the lock
with _ws_pin_lock:
    _ws_pin_verified[ip] = True
```

## PATTERN 37 — Client/Server Clock Skew Breaks Replay Window (Silent Drop)
**Problem:** Replay protection rejects any message whose timestamp difference is larger than a small window (e.g. 2s). Client/mobile clock is often skewed by seconds → **all** input events rejected **silently** → "everything is broken" even though connection is working
**Real Example:** This session — `if abs(time.time() - _ts/1000) > 2: return` threw away all mouse/keyboard events on a mobile with skewed clock


## PATTERN 41 — Fixed Quality + Unbounded Rate = Jitter on Weak Hardware
**Problem:** Server fixes quality (user choice) and lets capture/send rate run at maximum speed. On a weak CPU, frame encoding time is variable and close to the budget → fps and CPU oscillate violently (11↔30)
**Real Example:** This session — 2016 CPU (A12) gave a jittery counter and 30-44% unstable CPU usage


## PATTERN 67 — Extracting Mutable Scalar Config (int/bool): Snapshot Risk
**Problem:** When extracting settings to a module, the temptation is to move **all** settings including mutable flags (FLAG_SCALE, FLAG_GREY...). But if the setting is **scalar** (int/bool/str) and written live at runtime (from a handler like `/flags/update`), moving it to a module with an alias in the server (`FLAG_SCALE = pd_config.FLAG_SCALE`) **silently breaks live updates**: the alias takes a **snapshot of the value at import time**, so when the handler updates `pd_config.FLAG_SCALE` the old alias in the server doesn't change (because int/bool are passed by value not by reference — unlike dict/list). Result: feature "works" without error but with old value forever. Difference from Pattern 65: there dict/list can be shared by reference; here scalar is **impossible**.
**Rule:**
- Move **immutable constants only** (written once at import, read-only) — these are safe because there's no mutation.
- Mutable scalar settings: **leave them in place** until you do a redesign to a single object (`cfg.scale` instead of `FLAG_SCALE`) — then mutation via `cfg` reference appears everywhere.
- If you must move it before redesign: **convert all reads** to `pd_config.FLAG_X` (not alias) — never leave a scalar alias in the server.
```python
# Wrong (snapshot — silently breaks live-update):
FLAG_SCALE = pd_config.FLAG_SCALE      # took value now only
# Correct (either immutable in module, or direct read always):
if pd_config.FLAG_SCALE != 1.0: ...     # reads live value every time
```
- [ ] Is the moved setting immutable? If mutable scalar: did you avoid alias and use `pd_config.X` directly (or defer to redesign)? (Pattern 67)

The problem is especially common when users reorganize the project or move directories around.
**Real Examples:** PortDesk had `from portdesk_http import ...` and `import pd_config as ...` in SERVER.py, but those files live inside `modules/` — Python can never find them without a path injection.
**Rule:** The main file must include a bootstrap at its very top that auto-discovers the modules directory and adds it to `sys.path`. The bootstrap should:
1. Start from the main script's directory and walk upward searching for candidate directories (modules/, src/, lib/)
2. Verify that a candidate directory actually contains project files (marker files) to avoid adding a random directory
3. Support easy customization (directory names, marker file names)
```python
# ❌ WRONG — relies on implicit sys.path
import pd_config  # ModuleNotFoundError if modules/ not in sys.path

# ✅ CORRECT — bootstrap discovers modules dir first
MODULE_DIR_NAMES = ('modules', 'src', 'lib')
def _bootstrap_module_path():
    # ... auto-discover and add to sys.path ...
_bootstrap_module_path()
import pd_config  # now works regardless of directory layout
```
- [ ] Is there a bootstrap that auto-discovers the modules path before any project import? Does it support customization? (Pattern 70)

## PATTERN 71 — `from portdesk_server import ...` When the File Is Named SERVER.py
**Problem:** When a submodule (pd_routes.py) does `from portdesk_server import (app, cfg, ...)` but the main file is called `SERVER.py` (not `portdesk_server.py`), the import fails. Even if the filename is correct, `import portdesk_server` won't work when that file is running as `__main__` (Python registers it as `__main__` in `sys.modules`, not as `portdesk_server`).
**Real Examples:** pd_routes.py did `from portdesk_server import (...)` but the file was named SERVER.py, and Python never registered it under the name `portdesk_server` in `sys.modules`.
**Rule:** The main file must register itself in `sys.modules` under the canonical name that other modules import it by. Better yet, the importing module should use dynamic `sys.modules.get()` instead of a brittle `from X import`:
```python
# ❌ WRONG — brittle, depends on exact filename
from portdesk_server import (app, cfg, ...)

# ✅ CORRECT — dynamic, works regardless of main filename
import sys as _sys
_SERVER_MODULE_NAME = 'portdesk_server'
_server_mod = _sys.modules.get(_SERVER_MODULE_NAME) or _sys.modules.get('__main__')
globals().update({name: getattr(_server_mod, name) for name in _NEEDED_NAMES if hasattr(_server_mod, name)})
```
**In the main file:**
```python
# Register this file under the canonical name that pd_routes expects
if '__main__' in sys.modules and SERVER_MODULE_NAME not in sys.modules:
    sys.modules[SERVER_MODULE_NAME] = sys.modules['__main__']
```
- [ ] Is the main file registered in sys.modules under the correct name? Do submodules use dynamic import? (Pattern 71)

## PATTERN 72 — Dockerfile Does Not Copy the Modules Directory
**Problem:** When the main file is in the project root and modules live in a subdirectory, the Dockerfile must copy that subdirectory separately. Many developers forget `COPY modules/ ./modules/` in the Dockerfile, causing import failures inside the container that mirror the local failure. The problem is hard to detect because `docker build` succeeds (COPY does not error if the source files are not in the build context — it just copies an empty directory).
**Real Examples:** PortDesk Dockerfile had `COPY SERVER.py* ./` but no `COPY modules/ ./modules/` — the container would fail immediately at runtime.
**Rule:** The Dockerfile must copy every directory that contains imported Python modules. Also add a runtime check in entrypoint.sh:
```dockerfile
# In Dockerfile
COPY modules/ ./modules/
```
```bash
# In entrypoint.sh
if [ ! -d /app/modules ]; then
    echo "WARNING: /app/modules/ not found — server will likely fail"
fi
```
- [ ] Does the Dockerfile copy all module directories? Is there a check in the entrypoint? (Pattern 72)

## PATTERN 73 — Ghost Dependencies in requirements.txt After Library Replacement
**Problem:** When you replace an external library (like fastapi/uvicorn) with built-in code (like portdesk_http.py), you must remove the old library from requirements.txt. If you don't, `pip install` pulls in unneeded packages = larger Docker image + longer build time + potential version conflicts. Worse: a developer might think the project still depends on the old library and try to use it, creating hidden coupling.
**Real Examples:** PortDesk replaced fastapi + uvicorn + pyautogui + pyperclip with built-in modules, but requirements-docker.txt still listed `fastapi==0.115.6`, `uvicorn==0.34.2`, `pyautogui==0.9.54`, `pyperclip==1.9.0`. Also, `python-multipart` was incorrectly listed even though `portdesk_http.py` has its own built-in multipart parser.
**Rule:** Whenever you replace a library with a built-in module:
1. Remove it from both requirements.txt and requirements-docker.txt
2. Add a comment explaining what replaced it
3. Remove it from apt-get install in the Dockerfile if it needed system deps
```python
# ❌ WRONG — ghost dependency
# requirements.txt still lists the replaced library:
fastapi==0.115.6   # ← no longer used!

# ✅ CORRECT — removed with explanation
# NOTE: fastapi/uvicorn replaced by built-in portdesk_http.py
# NOTE: pyautogui replaced by built-in portdesk_input.py
# NOTE: python-multipart not needed — portdesk_http.py has built-in multipart parser
```
- [ ] Is every library in requirements.txt actually used in the code? Have replaced libraries been removed? (Pattern 73)
